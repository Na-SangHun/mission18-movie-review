## 원인별 효과 (한 가지만 바꾼 쌍끼리 비교)

| 바꾼 것 | 비교 | bs=1 | bs=32 | 해석 |
|---|---|---|---|---|
| 실행 엔진 PyTorch→ORT | A→C | 10.93→5.32 (2.05x) | 7.92→7.68 (1.03x) | batch가 커지면 차이가 사라짐 → bs=1 이득의 대부분은 계산이 아니라 **호출마다 드는 고정 비용** 차이 (PyTorch 쪽 오버헤드로 추정) |
| 그래프 최적화 | C→D | 5.32→4.78 (1.11x) | 7.68→6.88 (1.12x) | batch와 관계없이 약 1.1배 → 연산 합치기(fusion)로 **계산 자체**가 줄어든 효과 |
| INT8 양자화 (ORT) | D→E | 4.78→3.06 (1.56x) | 6.88→4.67 (1.47x) | batch와 관계없이 약 1.5배, 크기 54.1→14.0MB (3.9배↓) |
| INT8 양자화 (PyTorch) | A→B | 10.93→19.62 (0.56x) | 7.92→4.70 (1.69x) | bs=1에서는 **오히려 느림**: 호출마다 활성값 범위를 재고 양자화하는 고정 비용이 계산 절약보다 큰 것으로 보임. batch가 커지면 이득 |

## 정확도·예측 변화
- 모든 INT8 변형의 정확도 차이는 McNemar p ≥ 0.12 → FP32와 **통계적으로 차이 없음**
- reduce_range(F)는 예측이 바뀐 문장이 오히려 늘었음(29→41) → 이 모델·CPU 조합에서는 16bit 중간합 포화가 주된 문제라는 근거를 찾지 못함. 가중치를 7bit로 줄인 만큼 오차가 늘어난 것으로 보임(추측)
- E에서 FP32가 확신(≥0.9)했는데 뒤집힌 문장은 3개. 처음에는 "긴 문장이라 약하다"고 봤으나 **실험 결과 틀린 관찰이었음** → 원인 조사는 `investigate_flips.md` 참고
  - '좋은 주제곡, 매력있는 남녀 배우, … 구태의연한 내…': 0.94 → 0.02 (정답 부정)
  - '오늘 헤어졌어요 물론 차였죠 … 이영화를 봤…': 0.91 → 0.05 (정답 긍정)
  - '첨엔 흥미진진했으나갑자기 막장 …': 0.06 → 0.90 (정답 긍정)

## 결론: 서비스에는 E (ORT INT8 기본 설정) 사용
- 정확도는 FP32와 같고(89.00% / 89.05%, p=1.00), 크기 3.9배↓, bs=1 속도 3.6배↑ (PyTorch FP32 대비)
- G와 성능 차이가 거의 없어서 설정이 가장 단순한 E를 선택
- 서비스는 리뷰를 1개씩 분석하므로 bs=1 기준이 중요 → PyTorch 동적 양자화(B)는 이 상황에서 오히려 느려서 제외

## 트러블슈팅
| 증상 | 원인 | 해결 |
|---|---|---|
| `quantize_dynamic`에서 `FileNotFoundError: ...model_fp32-inferred.onnx` | 내부 C++ shape inference가 한글 경로(`1팀_나상훈`)를 못 읽어 중간 파일이 생성되지 않음 | Python으로 `onnx.load` + `infer_shapes`한 모델 객체를 경로 대신 전달 |
| reduce_range 변형(F)의 결과가 E와 완전히 같음 | `ReduceRange`를 `extra_options`에 넣어서 무시됨 | `quantize_dynamic(..., reduce_range=True)` 인자로 전달 |
| export 시 TracerWarning (패딩 마스크가 상수로 고정될 수 있음) | transformers 마스크 코드의 Python 분기 | 패딩이 섞인 batch에서 PyTorch↔ORT 최대 차이 1.76e-05로 문제없음을 확인 |
